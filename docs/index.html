01 / Title & Abstract

Can a simple scoring rule tell editors which pages to refresh first — and does it actually beat doing nothing clever at all?

FlyRank's editorial team had no consistent way to prioritize which content pages needed a refresh, relying on ad-hoc picks by age or traffic. This project frames the problem as ranking, not prediction: combine staleness, click performance, and search demand into a single priority score. A hand-weighted version of that score was tested with precision@20 against the simplest possible baseline — ranking by staleness alone — and it lost, 0.29 to 0.31. Rather than tuning the heuristic until it won, that result was kept as the finding: manual weights aren't reliable here, which is the direct argument for training a model on real historical outcomes instead of guessing at weights. That trained-model comparison is the next stage of this paper.

02 / Introduction

The decision this work supports

Editors need to decide, every week, which of thousands of pages to spend limited refresh capacity on. Individual signals — page age, current clicks, search demand — are visible separately, but nothing combines them into an ordered action list. The result is prioritization by gut feel: pick the oldest pages, or the lowest-traffic ones, with no consistent logic and no way to check afterward whether the choice was any good.

This paper treats the problem as a ranking task: editors don't need an exact forecast of future traffic, they need an ordered queue they can work down with confidence that the top of the list is genuinely worth acting on first.

03 / Data

Data

Two data sources were used across this project, both public-safe — no client names, domains, URLs, or credentials appear anywhere in this paper or the underlying notebooks.

Starter dataset

An anonymized content-refresh dataset of 30,000 rows across 32 anonymized clients (data/raw/content_refresh_anonymized.csv), used for early framing and the W02 baseline comparison.

Warehouse release

From Week 3 onward, the full gated Hugging Face warehouse (FlyRank/internship-warehouse), queried via DuckDB. All feature and label development uses the month=2026-03 partition. The warehouse's _sample table represents a later, sealed month and is used only to test query mechanics — never for feature or label development, to avoid any risk of the analysis leaking into evaluation.

Note on scope: the W05 trained-model stage below uses the starter CSV rather than the full warehouse — this keeps the model directly comparable to the W04 rule baseline, which was also built on the starter CSV. Expanding onto the full warehouse (with proper per-client time windows) is a natural next step once the starter-scale comparison holds up.

04 / Methodology

Methodology

Framing

The task is framed as ranking, not point prediction. Three observed signals — content staleness, current clicks, and search demand — are combined into a single priority score, normalized onto a common scale so no single metric dominates (clicks can run into the thousands; page age is measured in days).

Baseline

The baseline is deliberately simple: rank pages by staleness alone (days since last update), with no other signal involved. Any candidate scoring approach has to beat this before it earns any claim of being useful.

Signal verification

Two candidate signals were checked against the data before being trusted in a scoring rule:

SignalVerdictNote
StalenessMIXEDReverses direction in the 181+ day tier
CTR vs. search positionCONFIRMEDMonotonic drop as position worsens

Based on this, the scoring rule used is stale_and_ctr_underperform — pages flagged only when both staleness and CTR-vs-position underperformance agree, rather than trusting staleness alone given its mixed verdict.

Label & leakage discipline

An early proxy label, trend_direction, was found to be unreliable: percentage-change math on near-zero baseline traffic produces misleading swings — pages showing a nominal "up" trend of +58% despite zero clicks in both the before and after windows. This proxy is flagged for replacement with a proper future-window label in the modeling stage.

A leakage check was also run deliberately: using next-month impressions as a feature causes model AUC to spike toward 1.0 — an unambiguous sign of using information the model shouldn't have access to at prediction time. This trap is documented, not fixed away, as evidence of leakage awareness going into the modeling stage.

Trained model (W05)

Target: is_declining_label — 1 when trend_direction == "down", the same label the data dictionary defines and explicitly walls off from ever being a model input (along with trend_direction and trend_pct themselves).

Features: days_since_last_update, ctr, avg_position, impressions_90d, clicks_90d, engagement_rate, scroll_rate, content_age_days, word_count (numeric), plus position_tier, freshness_tier, content_type, main_intent (one-hot encoded). No product-flag or label-source columns anywhere in the feature set.

Split: client-holdout, not a random row split — 26 of 32 clients in train, 6 held out entirely for test. A random row split would let the model recognize a held-out client's own traffic level or content mix from other rows of that same client seen in training; grouping by client closes that gap.

Models: Logistic Regression (interpretable floor) and Random Forest (captures the staleness × CTR-gap interaction the W04 rule had to hard-code manually).

05 / Results

Results

Heuristic vs. baseline (W02)

The hand-weighted priority score was evaluated with precision@20 against the staleness-only baseline on the starter dataset:

0.29 Hand-weighted heuristic — precision@20
0.31 Staleness-only baseline — precision@20
Honest finding The heuristic lost to the simplest possible baseline. This result was kept as-is rather than tuned until it "won" — the finding itself is the evidence that manually chosen weights aren't reliable for this problem.

Ranked action queue (W04)

Applying the stale_and_ctr_underperform rule produced a ranked queue (work/outputs/baseline_action_score.csv), reviewed line-by-line for the top 10 flagged pages, including an explicit check of what evidence would make each flag wrong.

Trained model vs. baseline (W05)

The W04 rule, a Logistic Regression, and a Random Forest were all evaluated on the same held-out client split, against the same is_declining_label target:

Honest finding The W04 rule actually falls below random ranking at precision@50 (0.180 vs. a 0.391 base rate) on this held-out set of clients — the hand-built staleness-AND-CTR-gap condition doesn't generalize well to clients it wasn't built against. Random Forest is the clear winner on both cutoffs and beats random ranking comfortably, which the rule alone did not.

Random Forest's top features — impressions_90d (0.24), content_age_days (0.16), and avg_position (0.16) — are spread across several signals rather than dominated by one, which argues against leakage. All three make intuitive sense: higher-traffic, older, better-ranked pages are where a real decline is both easier to measure and more likely to reflect an actual trend rather than noise.

06 / Limitations & Honest Framing

Limitations

Findings in this paper are observed and directional, not causal — nothing here demonstrates a causal refresh impact on rankings, and none of it should be read as decoding a search engine's ranking algorithm.

  • Batch artifact in the staleness signal: 8,773 of 9,171 rows in the 91–180 day tier share an identical days_since_last_update value of 104 — a strong signal of a data collection artifact rather than genuine variation, not a property of the pages themselves.
  • Zero-click anomaly: a subset of pages register meaningful search demand alongside zero recorded clicks, worth flagging for review rather than treating as a real behavioral signal.
  • No per-client normalization: scores are currently comparable within the dataset as a whole, not fairly comparable across clients of very different scale.
  • Proxy label limitation: the trend_direction label used during framing is a percentage-change artifact, not a clean measure of real performance change (see Methodology).
  • The trained model's reliability is narrow: the Random Forest's error rate is 9.1% on top_3-ranked pages but 39–45% everywhere else (page_1, page_3_5, striking, deep) — it is currently only solidly trustworthy for the best-ranked tier.
  • Near-zero-traffic pages remain the hardest cases: the model's most confidently wrong predictions were all on pages with 1–3 total impressions over 90 days — exactly where the underlying label is noisiest, since a page moving from "1 click" to "0 clicks" registers as a full decline despite carrying almost no real signal.
07 / Ranked Recommendations

Action playbook

  1. Ship the Random Forest, not the W04 rule — the rule underperforms random ranking at precision@50 on held-out clients; the trained model beats both the rule and random ranking clearly.
  2. Restrict production use to the top_3 position tier for now — that's the only tier where the model's error rate (9.1%) is low enough to trust without manual review.
  3. Add a minimum-impression floor to the label itself before any further training — near-zero-traffic pages are the model's most confidently wrong cases precisely because the label is noise at that volume, not because the model is failing.
  4. Add per-client normalization before deploying any score across clients of different traffic scale.
  5. Exclude or repair the 91–180 day staleness tier until the batch artifact behind the repeated 104-day value is understood.
  6. Replace trend_direction with a proper forward-looking label before scaling this onto the full warehouse.
